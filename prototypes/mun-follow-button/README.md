# Native Mün follow-button prototype

The native implementation lives in `mun-frontend/src/components/FollowButton.mun` and follows `packages/frontend/src/components/MkFollowButton.vue` without changing the Vue application or backend. This directory contains isolated fixtures for it. It requires the Mün web renderer and its service adapter. The service adapter maps the component to the Misskey API, main-channel stream, login, confirmation, localization, preferences and achievement contracts. The fixtures supply deterministic dependencies; the app does not yet render the component. A future profile surface must provide its login, localization, confirmation, authenticated API, stream, haptic and achievement services, as well as Tabler icons and Misskey theme variables.

To run the interaction checks, install or link a built Mün checkout with `@mun/core`, `@mun/web`, `@mun/vite`, Vite and Playwright available under this directory's `node_modules`, then run `node adapter-test.mjs`, `node test.mjs` and `node parity.mjs`. Build `misskey-js` and run `node stream-test.mjs` and `node multi-stream-test.mjs` to exercise shared-channel behavior against the real SDK; set `MISSKEY_STREAM_MODULE` to its built `streaming.js` if it is elsewhere. Set `PARITY_BROWSER=webkit` to run the comparison in WebKit (Chromium is the default). The latter also requires Vue, `@vitejs/plugin-vue` and Sass, and compares the native button against the checked-out Vue component. The parity test requires the built `icons-subsetter` CSS and fonts in `packages/frontend/node_modules/icons-subsetter/built`; set `MUN_ICON_DIR` to their directory if they are elsewhere. If the Mün checkout is outside the repository, set `MUN_ROOT` to its path. For manual inspection run `node_modules/.bin/vite --config vite.config.mjs` and open `/fixture.html`.

The interaction fixture checks requests, state transitions, service-adapter wiring, and an initially-following server render. The stream tests use the real Misskey SDK with a fake WebSocket and verify event delivery and independent disposal of shared-channel consumers. The multi-component test mounts two compiled Mün buttons in JSDOM and exercises per-user updates and a mocked follow request; it does not connect to a real backend. It also connects the component to the native API transport and intercepts a complete authenticated HTTP request without contacting a backend. The controlled Vue comparison checks initial button text, dimensions, colors, icon classes, and screenshots with the built Tabler font for ten full, compact, and large states, plus follow, unfollow and request-cancellation interactions, declined login, confirmation cancellation, loading state, pending state and stream confirmation. Loading-spinner animation is frozen and forced visible for comparison; animation timing and responsive layouts remain untested. Screenshots allow a two-level color-channel tolerance for antialiasing. Neither fixture is a production integration. Since the compiler currently rejects `@State` initializers that reference view inputs, the view reads the input values until it initializes its state on appearance.

To validate a compiler that supports input-based `@State` initialization against the component before adopting it, set `MUN_COMPILER_MODULE` to its built `packages/compiler/dist/index.js` and run `node compiler-state-test.mjs`. This compiles a temporary revised version of the actual component; the committed component retains its workaround until the compiler change is integrated.

`node confirm-test.mjs` exercises the native follow confirmation service, and `node confirm-parity.mjs` compares warning/question layouts with the Vue dialog at mobile and desktop widths. Set `PARITY_BROWSER=webkit` for WebKit. The comparison stubs the modal shell and MFM renderer and freezes animations; progressive blur, rich MFM text and motion trajectories are not covered.
